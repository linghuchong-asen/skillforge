# 评审并提交代码

只有用户明确要求时才创建提交；除非用户在同一请求中另行要求，绝不 push。用户只要求评审、没要求提交时，做到第 2 步为止，汇报评审结论后停止。

流程分六步：查看工作区 → 代码评审 → 提交前检查 → 有针对性地暂存 → 撰写提交信息 → 提交并汇报。第 1、2、4 步偷懒，是不相关改动、遗留问题和运行时产物混进历史的根本原因，事后清理远比提交前花几分钟检查贵。

## 1. 查看工作区

先跑 `git status` 和 `git diff` 看到全部内容（包括未跟踪文件），再决定哪些属于用户要的这次提交。

- 工作区里混着多个不相关的改动时，建议拆成多个提交，并且只提交用户要求的那部分。绝不盲目 `git add -A` 或 `git add .`。
- 未跟踪文件只纳入改动真正需要的。数据文件（`.xlsx`、截图、抓取脚本）、本地笔记、本地工具目录这类几乎从不该进提交。
- 永不暂存：真实凭证、本地 `.env` 文件、数据库文件、生成的备份、运行日志，以及构建产物和生成文件的无关波动（`dist/`、`build/`、模式相关的生成文件等），除非用户明确要求。
- 认证凭据、API key、第三方凭证、重置令牌、审计数据、导出文件一律视为安全敏感——提交前把暂存 diff 完整重读一遍，专门找它们。

## 2. 代码评审

把完整 diff 当作一个待评审的 PR 通读一遍，再决定能否提交：

- **正确性**：边界条件、错误处理、并发与资源释放；逻辑是否与用户描述的需求一致。
- **测试**：行为改动是否有配套测试；测试是否真的覆盖新逻辑，而不是只跑通了旧路径。优先进程内 fake，而不是依赖外部网络的服务。
- **安全**：硬编码的密钥与凭证、注入与路径穿越、权限校验是否可绕过、导出数据是否泄露敏感字段。
- **遗留物**：调试输出（`console.log`、`print`、debugger）、注释掉的代码、写了一半的 TODO 方案。
- **仓库约定**：AGENTS.md / CLAUDE.md / CONTRIBUTING 的约定优先级最高；注释与文档语言、命名风格、错误处理惯例是否与周围代码一致。
- **关联改动**：改了对外行为却没同步文档、env 模板、示例配置、changelog 等关联文件。

小问题（格式、笔误、漏改）直接修掉再往下走；方向性问题（设计、方案、取舍）先停下来向用户说明并确认。修完任何代码后，重跑受影响的检查。

## 3. 提交前检查（按改动范围）

检查范围跟着改动走，不盲目全跑。仓库自己的 CI 配置（`.github/workflows/`、`.gitlab-ci.yml` 等）是权威检查清单；提交前覆盖受影响范围的完整检查，迭代过程中只跑最小相关测试没问题。

任何改动都要过的一条：`git diff --check`（空白错误）。

按技术栈信号判断（存在才跑）：

| 信号                                             | 检查                                                                                                                                                       |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `go.mod`（从该模块目录运行）                     | 改动的 Go 文件过`gofmt -w`；`go test ./...`、`go vet ./...`；装了 golangci-lint 就跑，版本以 CI 固定值为准                                                 |
| `package.json`                                   | 用项目 scripts 里已有的`lint`、`typecheck`、`test`；用户可见或影响构建的改动加 `build`；页面交互/布局改动加 e2e                                            |
| Python（`pyproject.toml` / `requirements*.txt`） | 按项目配置跑 lint（ruff 等）、类型检查（mypy 等）、pytest                                                                                                  |
| Makefile / justfile 有`check`、`test` 目标       | 优先用项目自己的目标                                                                                                                                       |
| 容器/部署文件、环境变量改动                      | 有 Docker 就渲染校验 compose 配置：`docker compose --env-file <env模板> -f <compose文件> config`；环境变量新增要同步 env 模板、compose、启动脚本和部署文档 |

仓库自带的其他检查手段（`tools/`、`scripts/` 下的 check 类脚本，pre-commit 框架、husky hooks）存在就一并跑。

- 某项检查本地跑不了（缺工具、缺 Docker、缺凭据）时，在最终汇报里明确说明，不要默默跳过。
- 失败要区分：是本次改动引入的，还是基线分支上本来就有的。基线已有失败同样阻塞交付，除非用户明确接受。

## 4. 有针对性地暂存

`git add` 指定路径，然后从头到尾读一遍 `git diff --staged`：内容应恰好是用户描述的改动，没有调试残留、没有密钥。多出来的从暂存区移除。

## 5. 撰写提交信息

Conventional Commits 结构用英文，主题行用简体中文：

```
<type>(<scope>): <简体中文主题>
```

- **type**：`feat`、`fix`、`docs`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`style`、`revert`。破坏性改动在冒号前加 `!`。
- **scope**（可选）：组件名，小写 kebab，如 `auth`、`ui`、`api`；改动横跨全部时省略。
- **主题**：简体中文，说明改动做了什么。无句尾句号；整行不超过 72 字符；协议名、标识符、单位（如 PostgreSQL、`/v1`）保持原文不翻译。
- **正文**（仅当主题说不清改动时才写）：解释为什么，跨组件改动按组件一条要点。正文用中文，但路径、命令、标识符、日志摘录保留原文；约 72 字符换行。
- 不加 AI 署名尾注（如 "Generated with ..."）。

好的示例——单行修复：

```
fix(auth): 修复令牌刷新后旧令牌未失效的问题
```

好的示例——带正文的功能提交：

```
feat: 新增导出数据的 CSV 格式支持

导出接口新增 format=csv 参数：表头本地化、RFC 4180 转义、流式写出避免
大数据集占用内存；JSON 导出行为不变。

- backend: CSV 序列化与格式参数校验，含边界用例测试
- docs: API 文档补充 format 参数说明
```

反面示例：`发版`、`自动更新`、`登录授权` 这类一个词或光秃秃名词短语的主题让历史无法检索；改动值得提交，就值得一句话说清。

写好commit信息后要弹窗提示，我来确认commit信息。

## 6. 提交并汇报

用 heredoc 提交，保证正文不被 shell 引号破坏：

```bash
git commit -m "$(cat <<'EOF'
feat(scope): 简体中文主题

正文……
EOF
)"
```

提交后汇报：commit hash 和主题、评审发现并修掉的问题、跑了哪些检查及结果、哪些检查跑不了、暂存时特意排除了什么。不 push。
